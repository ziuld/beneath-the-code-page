PROJECT CONTEXT

Beneath the Code is a developer platform connected to a future YouTube/software-education brand.

Its purpose is to combine:
1. Practical developer tools.
2. Deep software-engineering education.
3. Professional Java architecture.
4. Strong security and privacy.
5. A distinctive calm, cinematic developer experience.

The brand philosophy is:
- Understanding over memorisation.
- Clarity over spectacle.
- Calm, precise, premium technical communication.
- Systems thinking rather than shallow tutorials.

MVP

No users/accounts in Phase 1.

Initial developer tools:
- JSON Formatter
- JSON Validator
- JSON Minifier
- JSON → YAML
- YAML → JSON
- Base64 Encoder/Decoder
- UUID Generator
- JWT Decoder

These tools should execute in the browser whenever that is safer and more efficient.

Tool payloads such as JSON, YAML and JWTs must not normally be transmitted to the backend, persisted, logged, or sent to analytics.

The site also contains a Learn section.

The first free course is:
Java Fundamentals

The course should teach mental models and explain what happens beneath Java rather than being only a syntax tutorial.

INTERNATIONALISATION

MVP languages:
- English
- Spanish
- French

No user-facing text should be hard-coded.

Locale resolution should consider:
1. Explicit user selection.
2. Persisted preference.
3. Browser language.
4. Configured country default where appropriate.
5. English fallback.

Spain should default appropriately to Spanish, France to French, and English is the general fallback. Multilingual countries must not be handled with simplistic assumptions.

ARCHITECTURE

The agreed server stack is:

Java
Spring Boot
Spring MVC
Thymeleaf
Spring Security

Spring Boot is the deployable application.

Spring MVC is the web adapter used by Spring Boot.

Thymeleaf performs server-side HTML rendering.

Typical request:

Browser
→ HTTP GET/POST
→ Spring Boot
→ Spring MVC controller
→ application/use case where required
→ view model
→ Thymeleaf
→ HTML
→ Browser

This is NOT a React/Vue SPA.

TypeScript is used selectively for:
- browser-local developer tools;
- CodeMirror integration;
- reusable interactive behaviour;
- browser-side functionality where Java/server interaction is unnecessary.

HTMX may be used for targeted server interactions and HTML-fragment replacement when useful, but should not be introduced without a reason.

The system should initially be one deployable Spring Boot application.

It should remain stateless where practical so that future horizontal scaling can be:

Internet
→ Load Balancer
→ N identical Spring Boot instances

Do NOT introduce microservices in the MVP.

If a future capability genuinely requires independent scaling, isolation, lifecycle, runtime requirements, or ownership, it may later be extracted into a service.

The Spring Boot application can then operate as the browser-facing BFF and orchestrate those services.

Microservices are an evolutionary option, not a target architecture by themselves.

ARCHITECTURAL STYLE

Use:
- Hexagonal Architecture
- Clean Architecture principles
- SOLID
- capability-oriented/modular organisation
- explicit dependency direction
- pragmatic abstractions

Do not create interfaces or layers merely to make the project appear “hexagonal”.

Domain code must not depend on Spring or infrastructure.

Infrastructure may depend inward.

Controllers should remain thin.

Business/application logic must not accumulate in controllers.

Folder names alone do not constitute architecture; dependency direction and responsibility boundaries matter.

FRONTEND / SSR

The project is server-rendered first and browser-enhanced where appropriate.

Thymeleaf builds pages on the server.

TypeScript does not own global application routing or replace server-side rendering.

For example:

GET /tools/json-formatter
→ Spring Boot
→ Thymeleaf
→ HTML
→ browser

Then:

User pastes JSON
→ browser TypeScript
→ local processing
→ result

No POST containing the user's JSON is required.

VISUAL DIRECTION

The initial visual direction has been approved.

It combines:
- cinematic editorial identity;
- precise developer workspace;
- near-black backgrounds;
- warm ivory/off-white typography;
- graphite surfaces/borders;
- restrained monochrome presentation;
- large negative space;
- wireframe software/system structures;
- subtle flowing contour/data lines.

Avoid:
- cyberpunk;
- gaming UI;
- excessive glow;
- purple SaaS gradients;
- generic glassmorphism;

Use three typography roles:
1. Editorial/display serif for major brand/course statements.

Marketing/learning areas can be more cinematic.

- reduced-motion support;
- contrast compliance;

SECURITY

Security is part of the architecture from the beginning.

Use Spring Security even though Phase 1 has no authentication.

Design towards applicable OWASP ASVS controls.

Important areas:
- HTTPS for production
- restrictive CSP
- secure HTTP headers
- output encoding
- input validation
- safe YAML processing
- request/resource limits
- rate limiting where relevant
- secure errors
- dependency scanning
- secret detection
- SAST
- container hardening
- secure logging
- supply-chain awareness

Never expose stack traces to users.

Never log developer-tool payloads, JWTs, secrets or similar sensitive input.

PRIVACY

The UI should make local processing clear where appropriate:
“Processed locally in your browser. Your content is not sent to Beneath the Code.”

LOCAL DEVELOPMENT / DEPLOYMENT

Cloud hosting, production infrastructure and broader deployment architecture are Phase 2 decisions.
